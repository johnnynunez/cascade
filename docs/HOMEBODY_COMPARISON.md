# HomeBody comparison and proposed CASCADE follow-ups

Reviewed 2026-10-02. This is a source review and design proposal, not a HomeBody port or a new physical validation. It extends [Robot modularity](ROBOT_MODULARITY.md); the current refusal of unadmitted mobile manipulation and whole-body actuation remains in force.

## What is public

HomeBody describes VLM-directed navigation, manipulation and drawer skills with spatial memory. Robot exploration supplies images, joints, waypoints and SLAM geometry for an Isaac Sim twin; Super Odometry and ICP connect remembered views to a common frame. Skills combine segmentation/stereo grounding, tracking, visual correction and bounded retries. Reported arm/hand commands run at 250 Hz; the learned AMO lower-body policy runs at 50 Hz. Removing an intermediate VLA therefore does not remove learned control. Some figures and the interactive cleanup are explicitly illustrative. Videos provide no aggregate success measurement. The site also reports endurance and servo-heating limitations. [Project presentation](https://tml.stanford.edu/homebody/).

The linked repository at [`6c6d7217bae5099408613b6befb502c9b5986e0b`](https://github.com/Stanford-TML/homebody/tree/6c6d7217bae5099408613b6befb502c9b5986e0b), committed 2026-10-01, contains the README and presentation assets/scripts, not the robot skill/controller implementation. Its [release schedule](https://github.com/Stanford-TML/homebody/blob/6c6d7217bae5099408613b6befb502c9b5986e0b/README.md) marks SIM (October 4), REAL2SIM (October 11) and REAL (October 18) as planned. There is consequently no published HomeBody Python API, controller transport contract, dependency lock or reproducible robot evaluation to import at this snapshot. The [page source](https://github.com/Stanford-TML/homebody/blob/6c6d7217bae5099408613b6befb502c9b5986e0b/docs/index.html) makes Paper a pending span without a paper URL; a primary arXiv title search found no paper. This is a publication-status observation, not a claim that no manuscript exists.

No repository-level project license was present. [Web dependency notices](https://github.com/Stanford-TML/homebody/blob/6c6d7217bae5099408613b6befb502c9b5986e0b/docs/LICENSES.txt) cover Three.js, fonts, icons and HLS.js; they do not establish a license for the unreleased robot software or all demonstration assets. No code, weights or media were copied into CASCADE.

AMO's G1 example cannot consume MicroDuck's 61-observation/14-action contract or BAM calibration. Reusing a policy requires the complete embodiment, actuator, observation, command, checkpoint and clock contracts plus native validation; matching an ONNX/TorchScript tensor shape is insufficient.

## Proposed CASCADE changes

The following are our design recommendations. They are not implemented by this document and do not assert that HomeBody has the same contracts.

| Priority | Concrete extension and existing boundary | Acceptance evidence before motion use |
| --- | --- | --- |
| 1 — Grounded memory | Extend [beliefs](../src/cascade/memory/beliefs.py) and [episodic keyframes](../src/cascade/memory/episodic.py) with immutable observation IDs, image hashes, map ID/epoch, pose-at-capture, calibration ID and transform provenance. Current object positions are base-frame values; do not reinterpret them as global locations after walking. Retrieval proposes a viewpoint or search region, followed by fresh localization. | Recorded replay with an occluded object, a moved base, two similar objects and a map reset. Old memory may guide search but cannot authorize grasp geometry. Persistent storage must retain age across process restarts. |
| 2 — Dynamic frames | Add a typed transform provider alongside [passive sensor envelopes](../src/cascade/sensing/models.py): explicit source/target frames, units, handedness, capture clock, validity interval, localization uncertainty and map epoch. Compose camera→torso→map transforms at capture time, not at tool-call time. Bind any image-point request to the exact image and normalization convention. | Reject stale transforms, changed calibration, invalid depth, map re-localization jumps and observations from another episode. Demonstrate known point reprojection and transform closure with measured error budgets. A static arm `base_pose` does not satisfy this contract. |
| 3 — Auditable reconstruction | Define a reconstruction manifest binding original observations, SLAM data, transforms, mesh/collider hashes and alignment residuals. Store measured, inferred and unknown geometry separately; retain unknown space in navigation/manipulation checks. Use the independent episode binding in [evaluation adapters](../benchmark/arena/README.md) for later trials. | Evaluate held-out metric landmarks, scale, collision geometry and camera reprojection. A matched screenshot or successful final benchmark predicate cannot certify the twin or real contact. |
| 4 — Local correction and retries | Add an optional bounded tracking/correction provider behind existing skill execution. Keep candidate changes inside the owning skill, with fresh observations, cancellation checks, collision checks and per-attempt receipts. Expose typed failure reasons to the [skill graph](../src/cascade/robotics/graph.py); use finite explicit recovery branches. | Inject lost tracking, stale masks, no contact, exhausted budget and stop during retry. Preserve every refuted/unverified attempt and verify the final physical effect independently; recovery cannot silently clear the stop latch or erase earlier graph failures. |
| 5 — Health-aware execution | Propose a separate typed health payload for measured temperature, current, battery and fault state, including units, validity and device-specific limits. It does not yet exist in the sensor model. Let the actuator owner apply declared derating/hold behavior and reject a new attempt when health is unknown under a required health contract. | Sensor dropout, overtemperature and stalled actuator tests must reach the owner's stop path without an LLM round trip. Do not treat estimated tactile force or commanded effort as a temperature/current measurement. |
| 6 — Future whole-body owner | Retain optional learned policies behind skills, while one controller owns the entire command endpoint through the [resource catalog](../src/cascade/robotics/resources.py). Arm goals, gait and torso requests must enter that owner coherently; separate CASCADE domains must not publish competing whole-body packets. Define rates/decimation, bounded command age and balance-preserving stop explicitly. | Begin with an isolated native controller test: measured support, no forbidden body support, joint/torque limits, perturbations, interrupted skills and safe retained stop. Then validate mobile manipulation with dynamic frames. Current MicroDuck locomotion admission and mixed-physical-actuation restrictions remain unchanged. |

The first useful increment is a **read-only, source-bound exploration replay** exercising memory retrieval and transform invalidation through the existing sensing/runtime interfaces. It can establish data-contract correctness before adding robot actions. A later tabletop correction experiment can measure tracking and retry behavior within an already admitted arm configuration. Whole-body G1 or MicroDuck activation is a separate milestone; neither this comparison nor the modularity CI supplies that proof.

## Validation scope

This review inspected primary project pages, pinned upstream sources/licenses and the linked CASCADE modules. It did not install dependencies, download checkpoints, execute external robotics code, run a simulator or measure HomeBody. Only this Markdown file was added. Revisit the HomeBody release schedule and actual implementation before selecting its future adapter or copying software.
