# Legacy task completion and effect evidence

A completed actuator routine cannot make `task_done(success=true)` confirm an unknown physical effect. The legacy `SkillRuntime` now keeps an explicit task ledger for the skills registered in `agent.effects.POSTCONDITIONS`, matching the cumulative completion rule already used by the composed runtime. The actor's result dictionary and the LLM's completion claim cannot supply the ledger's postcondition.

Each registered call creates an obligation before preparation or actuation, with a fresh task ID, a sequential action ID and the resolved arm identity. The local checker must return a matching skill/kind confirmation, and execution must have completed successfully without uncertain delivery. A missing checker, missing verdict, contradiction, execution failure, malformed result, preparation exception or cancellation leaves a non-confirmed obligation. A `finally` path releases pending ownership even if the call is interrupted after verification but before its trace completes.

Debt remains for the whole task. A later read, another successful motion, a call on another arm, `reset_scene`, or `task_done(success=false)` cannot repair or erase it. A repeated motion also cannot silently supersede a failed one. Supporting an explicitly adjudicated recovery would require an additional admission policy; this change does not infer one from a later success.

`begin_task()` is a host API, not a tool or a tool argument. `AgentOrchestrator.run_task()` invokes it before reflex/experience/LLM dispatch. It rejects rebinding while an effect call is active and never resets the world, possession state, stop latch or controller. The manipulation domain adapter also forwards an explicit composed task boundary; passive sensor domains remain unaffected. Direct callers that do not establish a new host boundary retain their current ledger.

Both legacy `task_done` and the orchestrator's final `TaskReport` consult the ledger. Fast paths cannot train a successful reflex or finish with success while an obligation remains unknown. Pure read-only tasks can still succeed, and a confirmed multi-step task may end with a read-only call. This is not a rule about the last tool.

Every normal report exit, including an exhausted step budget, retains unresolved effects in both `TaskReport.unverified` and the trace summary. A failed reflex/experience attempt stays in the returned tool history when execution falls back to the LLM; each row identifies its tier, and its step index remains local to that tier. Beginning the next trusted task does not alter the already returned report.

Cancellation remains an exception. The composed runtime records an interrupted motion as unverified before releasing its admission slot, then propagates `KeyboardInterrupt`, `SystemExit`, or other `BaseException` interruptions. A caller that catches the interruption cannot obtain successful global completion by issuing a later successful motion. Interrupted reads create no physical obligation. This also closes a composed cancellation gap that existed before the legacy-ledger change; it does not claim that any retained physical episode exhibited that gap.

This change preserves existing individual skill return conventions and checker contracts. In particular, `move_home` still uses its historical commanded-home checker; this ledger does not upgrade that to independently measured settling. Cosmetic skills and composites absent from `POSTCONDITIONS` gain no new physical validation. The ledger cannot infer that an unexecuted natural-language goal was satisfied, and does not implement a general task planner, external-host task ownership protocol or physical stop verification. `turn_screw` remains unverified until an admitted fastener observer is integrated.

The causal baseline is source `8a62a49f465969ff8d104fce505b8e5c0644fd28`: both direct LLM and failed-reflex paths returned task success after an unverified screw effect. The same two observable completion tests fail on that baseline, while the read-only control passes. Final CPU evidence, retained initial failures and source hashes are recorded in [the completion receipt](../benchmark/results/legacy_task_completion_20261003.json). No physical validation is claimed.

The terminal-report follow-up reproduced three software counterexamples on `381d65ff5a36c0a862a7c0c7a2ac9a3b2425538a`: two exhausted reports omitted their existing debt, and one composed cancellation allowed global completion. The two ordinary exception/normal controls passed. After the correction, 141 focused CPU checks passed, including task boundaries, both dispatch tiers, cancellation propagation, read-only completion, ordinary MCP and the mock CLI.
