### Language-conditioning interface
Inputs are exactly three: variable number of **224×224 RGB frames**, **proprioception vector**, and **one language-instruction string**; output is a continuous action chunk from a flow-matching DiT (4-step denoising at inference) ([N1.5 model card](https://huggingface.co/nvidia/GR00T-N1.5-3B); [N1 paper](https://arxiv.org/html/2503.14734v2); [developer.nvidia.com/isaac/gr00t FAQ](https://developer.nvidia.com/isaac/gr00t)). It is a flat single-instruction API — no dialogue, no clarification, no task decomposition. N1.7 adds "explicit task/subtask decomposition" for long-horizon workflows ([embodiedglobal](https://embodiedglobal.com/en/article/gr00t-n1-7-isaac-teleop-apache2-lerobot-cosmos-reason2-qwen3-vl-droid-f6), **UNCONFIRMED** vs. first-party docs).

|---|---|---|---|
| RTX 5090 | 58 ms (17.3 Hz) | 37 ms (27.3 Hz) | **31 ms (32.1 Hz)** |
| H100 | 77 ms (13.0 Hz) | 38 ms (26.3 Hz) | 36 ms (27.9 Hz) |
| RTX 4090 | 82 ms (12.2 Hz) | 44 ms (22.8 Hz) | 43 ms (23.3 Hz) |
| Jetson Thor | 117 ms (8.6 Hz) | 105 ms (9.5 Hz) | 92 ms (10.9 Hz) |
| Jetson Orin | 300 ms (3.3 Hz) | 199 ms (5.0 Hz) | 173 ms (5.8 Hz) |

Community timing for N1: VLM 22.9 ms + 4×9.9 ms action head = 62.5 ms full model, "4 denoising steps are sufficient" ([mschweig fork README](https://github.com/mschweig/isaac-gr00t)).
- N1.7 (third-party summary of NVIDIA's deployment guide): H100 85.8 ms eager / 48.6 ms compile / **27.9 ms TensorRT (35.9 Hz)**; **L40S-class ("L40") eager 128.3 ms (7.8 Hz)** ([ay-robots.com](https://www.ay-robots.com/blog/en/run-gr00t-inference-without-a-local-gpu), citing [Isaac-GR00T deployment README](https://github.com/NVIDIA/Isaac-GR00T/blob/main/scripts/deployment/README.md)) — **UNCONFIRMED** until read from the repo directly.

### Control-rate requirements (action chunking)
From NVIDIA's official [real-world deployment guide](https://github.com/nvidia/isaac-gr00t/blob/main/getting_started/real_world_deployment.md):
- Robot **action-execution / camera rate: 30 FPS recommended**; the **model inference rate ≈10 Hz is the recommended minimum** for typical manipulation ("below 10 Hz suitable only for slow, non-reactive tasks" per [hardware recommendation guide](https://github.com/NVIDIA/Isaac-GR00T/blob/main/getting_started/hardware_recommendation.md), via [ay-robots](https://www.ay-robots.com/blog/en/run-gr00t-inference-without-a-local-gpu)).
- Default **action chunk = 16 steps** (≥32 when using Real-Time Chunking); a ~10 Hz policy drives a 30 FPS arm via chunking + asynchronous inference.
- Synchronous single-step control needs end-to-end latency < ~33 ms at 30 FPS — "capture, network, inference and post-processing often exceed 33 ms combined" → NVIDIA's own recommended pattern is **async inference + receding horizon (+ RTC, currently experimental and not wired into `Gr00tPolicy`/server path)**.
- Deployment splits inference from control: **ZMQ server–client** ("move compute-intensive inference to GPU servers, keep robot-side control lightweight") — the same pattern applies to sim clients.

## 3. Isaac Sim / Isaac Lab: two robots + cameras, photoreal, one GPU?

- **Multi-robot in one stage is routine.** Isaac Sim's own KPI suite steps **10 O3dyn robots** at 32–35 Hz physics on one RTX PRO 6000 Blackwell, and its ROS2 SIL benchmark runs a robot with **11 sensors (3 lidars + 4 stereo camera pairs, 8×1920×1200 render products)** ([Isaac Sim benchmarks](https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/benchmarks.html)). Isaac Lab ships **official multi-agent environments** (e.g., Shadow-Hand-Over: one hand hands an object to the second; IPPO/MAPPO via skrl) ([Isaac Lab environments docs](https://isaac-sim.github.io/IsaacLab/v1.4.1/source/overview/environments.html)).
- **Measured single-GPU throughput (RTX PRO 6000 Blackwell WS, official KPIs)**: Full Warehouse photoreal scene **153–160 FPS** (no robot cameras); Isaac ROS sample scene 48–52 FPS; ROS2 render+publish with the 11-sensor suite **~26–39 FPS**; docs example for the camera benchmark: 2×720p cameras ≈ 45 FPS ([benchmarks page](https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/benchmarks.html)). Interpolation: **2 robots × 2 cameras each at ≤720p in a tabletop scene lands in the real-time band (≥30 FPS) on one RTX PRO 6000**, with headroom shrinking fast with camera count/resolution. NVIDIA's own optimization tips: "use as many GPUs as cameras to maximize throughput"; camera rendering "most effectively scales with the number of GPUs" (same page).
- **Rendering quality knobs:** Isaac Lab's RTX renderer defaults to **DLSS** denoising (raster+RT hybrid); DLAA / DL-denoiser raise quality at a performance cost; path-traced mode is the expensive extreme ([Isaac Lab rendering guide](https://isaac-sim.github.io/IsaacLab/develop/source/how-to/configure_rendering.html)). Full path tracing for two live robot cameras at 30 Hz on one GPU has **no published NVIDIA benchmark** — treat as out of budget; DLSS raster ("photoreal-adjacent") is the realistic target.
- **Policy-in-the-loop eval precedent:** [Isaac Lab-Arena](https://github.com/isaac-sim/IsaacLab-Arena) (open-source, alpha v0.2.x) is NVIDIA's framework for exactly this SIL pattern — GR00T N / Pi / SmolVLA policies evaluated in Isaac Sim environments, integrated with LeRobot EnvHub; Lightwheel published **250+ RoboCasa/LIBERO tasks** on it ([NVIDIA/HF blog](https://huggingface.co/blog/nvidia/generalist-robotpolicy-eval-isaaclab-arena-lerobot); [developer page](https://developer.nvidia.com/isaac/lab-arena)). Arena's `lerobot-eval` runs the policy as a separate process from the sim — the standard decoupling.
- **GR00T-Dreams / DreamGen** is a *data-generation* blueprint (Cosmos world models → synthetic trajectories from one image + language), not a live-demo runtime ([NVIDIA/GR00T-Dreams](https://github.com/nvidia/gr00t-dreams); [DreamGen paper](https://arxiv.org/abs/2505.12705)). Relevant here as the sanctioned way to mint finetuning data for a custom two-arm rig.
- **Two GR00T-driven robots cooperating in one photoreal Isaac Sim stage: no published NVIDIA demo found** (searched GTC 2025/2026 coverage, Isaac blogs, Arena docs). Closest precedents: (a) GR00T-N1-2B's real-robot eval explicitly included **"Industrial multi-robot coordination with handoffs"** ([N1-2B model card](https://huggingface.co/nvidia/GR00T-N1-2B/blob/main/README.md)); (b) partner demo at GTC March 2026: Humanoid's KinetIQ — **two wheeled manipulators taking booth visitors' voice requests, dynamically allocating tasks and physically handing items over**, built on Isaac Sim/Lab + adopting GR00T N1.7, with an LLM-style fleet brain doing the decomposition ([thehumanoid.ai press release](https://thehumanoid.ai/humanoid-brings-voice-controlled-robotic-fulfillment-powered-by-kinetiqto-life-at-nvidia-gtc/); [NVIDIA GTC 2026 live blog](https://blogs.nvidia.com/blog/gtc-2026-news/)).

## 4. Open-ended language tasking of a VLA — precedents & limits

- **Benchmarked language following is on short, templated commands** ("pick the apple from table to plate"). N1.5's headline improvement over N1 is precisely language following on real GR-1 pick-and-place — N1 "consistently picks *some* fruit" but ignores which one; N1.5 has a "much higher language following rate" ([GEAR N1.5 page](https://research.nvidia.com/labs/gear/gr00t-n1_5/)). N1.5 was validated on "Language Table" and 5 sim GR-1 language tasks (same page). N1 reports LIBERO/DexMG/RoboCasa sim benchmarks + language-conditioned bimanual GR-1 tasks ([N1 paper](https://arxiv.org/abs/2503.14734)).
- **Novel-verb / novel-object generalization requires synthetic data, not prompting.** DreamGen exists because the base policy doesn't generalize to unseen verbs/environments; it lifts GR-1 humanoid success 37%→46.4% (avg of 4 tasks) using video world models to synthesize new behaviors from language ([DreamGen paper](https://arxiv.org/abs/2505.12705); [GR00T-Dreams repo](https://github.com/nvidia/gr00t-dreams)). N1.7 credits "improved generalization and language-following" to 20K h of EgoScale human video ([repo README](https://github.com/NVIDIA/Isaac-GR00T)).
- **No published NVIDIA demo of the public typing arbitrary free-form commands to raw GR00T live.** Found instead: (a) fine-tuned GR00T N1.5 on Jetson Thor executing a *fixed* typed command ("Pick the cube and put it in the bucket") on an SO-101 ([Advantech deep-dive](https://ess-next.edgecenter.io/en/posts/20260107133027/)); (b) the KinetIQ two-robot voice demo above, where **an orchestration brain interprets the request and dispatches robot skills** — i.e., the exact LLM-decomposition architecture cascade proposes; (c) GTC 2026 show-floor robots that "handed attendees the items they requested" ([GTC 2026 live blog](https://blogs.nvidia.com/blog/gtc-2026-news/)). Pattern across all precedents: **free-form language is handled above the VLA; the VLA executes atomic skills**.
- Embodiment coupling: every GR00T inference/finetune requires an `--embodiment-tag`; zero-shot works only on **pretrain embodiments** (GR-1, Unitree G1, bimanual YAM, AGIBot Genie1, RoboCasa Panda, DROID…); a custom two-arm rig is a `NEW_EMBODIMENT` finetune ([repo](https://github.com/NVIDIA/Isaac-GR00T)).

## 5. Latency-budget arithmetic (one GPU vs two)

Inputs: GR00T-N1.6 ≈ **31–44 ms/inference** on RTX-5090-class TensorRT/compile (§1); chunk = 16 actions executed at 30 FPS = **533 ms of motion per inference**; NVIDIA-recommended replan floor ≈ **10 Hz**; Isaac Sim photoreal tabletop + 4 cameras ≈ 30–60 FPS on one RTX PRO 6000 (§3); physics step 60–120 Hz is cheap relative to rendering ([benchmarks](https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/benchmarks.html)).

- **Shared single GPU (sim + 2× VLA):** two policies replanning at 10 Hz cost 2 × 10 × ~40 ms ≈ **800 ms of GPU time per second** just for inference — leaves <20% of the GPU for rendering+physics → guaranteed frame hitching and inference jitter. At a relaxed 4 Hz replan (execute 8 of 16 chunk steps ≈ 267 ms per call, per NVIDIA's own eval default of horizon 8) the two policies cost ~320 ms/s ≈ 32% GPU → borderline feasible with DLSS raster and 224×224 policy cameras, but with no headroom for the LLM orchestrator.
- **Standard mitigation #1 — split GPUs.** NVIDIA's deployment guide already ships the ZMQ policy-server split ([real_world_deployment.md](https://github.com/nvidia/isaac-gr00t/blob/main/getting_started/real_world_deployment.md)); Isaac Sim docs say camera rendering "scales most effectively with number of GPUs" ([benchmarks](https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/benchmarks.html)); and the DGX Station for Windows SKU institutionalizes it: **GB300 for model inference, add-in RTX PRO 6000 for ray-traced visualization** ([DGX Station for Windows](https://www.nvidia.com/en-us/products/workstations/dgx-station-for-windows/)). Cleanest demo architecture: **sim + render on RTX PRO 6000 (x86 box or Station add-in card), GR00T ×2 + LLM/VLM orchestrator on GB300** (748 GB lets the orchestrator be a large model, e.g., GPT-OSS-120B-class runs locally per [DGX dev guide](https://docs.nvidia.com/dgx/dgx-station-development-guide/Intro.html)).
- **Standard mitigation #2 — action chunking + async inference** (execute chunk while next inference runs; receding horizon; RTC experimental) — first-party guidance, §1.
- **Standard mitigation #3 — MIG partitioning**: RTX PRO 6000 up to 4 isolated instances; GB300 up to 7 ([androidhire](https://androidhire.com/nvidia-rtx-pro-6000-blackwell-workstation-edition); [DGX datasheet](https://gpusolutions.hrp.hu/wp-content/uploads/2026/05/dgx-station-datasheet.pdf)) — isolates inference jitter from rendering, at fixed capacity split. Note Isaac Sim itself is not documented to run inside a MIG slice (**UNCONFIRMED**).
